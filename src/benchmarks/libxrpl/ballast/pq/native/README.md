# Native PQ transaction checkpoint

This target builds the pinned candidate fork's unmodified beast, basics, json,
crypto, git, and protocol sources. It exercises actual XRPL serialization,
`SerialIter` parsing into `STTx`, and `STTx::checkSign()`. It is a focused
protocol-source build, not a full server build or a network deployment.
Archive extraction is the sole source exclusion, matching the earlier
secp256k1 control. `native-sources.txt` records the compiled C++ source list.

The parent [crypto checkpoint](../README.md) supplies revision checks and the
reference archive. The native executable links the candidate's actual
`SecretKey.cpp`, including its `randombytes` adapter backed by `cryptoPrng()`.
It does **not** link the primitive test executable's fixed-entropy adapter.
No candidate protocol source or root protocol source is edited.

## Execution flow

In [PqTransaction.cpp](../../../../../tests/libxrpl/ballast/PqTransaction.cpp):

1. `generateSeed("ballast/ml-dsa-44/accountset/v1")` derives an XRPL seed.
   `generateKeyPair(KeyType::Dilithium, seed)` exercises the fork's custom
   seed expansion and public-key recovery. A separate test compares its full
   public and expanded secret keys to OpenSSL's independently derived keys.
2. `makeSignedAccountSet()` sets transaction type AccountSet, account derived
   from that public key, Sequence 1, fully canonical flag, Fee 10 drops, and
   the 1312-byte SigningPubKey. The fee is a fixture constant, not validated.
3. `STTx::sign()` obtains the actual transaction signing payload and invokes
   the fork's signing dispatch. The payload includes the top-level public
   key and omits `TxnSignature`. The candidate's normal randomized signing
   remains enabled.
4. `getSerializer().getData()` creates owned wire bytes. `SerialIter` reads
   those bytes, and `STTx{iterator}` constructs the parsed transaction. The
   owning wire vector outlives the iterator. No ownership optimization is used.
5. `checkSign(quantumRules)` recognizes the key through
   `enabledPublicKeyType`, which requires `featureQuantum`, then calls the
   fork's real signature verifier. The test also asks OpenSSL to verify the
   signature against the same signing payload. The full wire bytes must fail
   as a substitute signing payload.

`Rules` retains a reference to the preset set; the fixture declares that set
before the Rules object so it remains alive until after Rules is destroyed.
Enabling `featureQuantum` is a **local test configuration**, not evidence that
any live network has activated it.

Additional checks cover Sequence tampering, rejection when Quantum is
disabled, acceptance of an OpenSSL-produced signature on the actual payload,
and a secp256k1 control with the original checkpoint's transaction ID. A
different claimed Account can still pass the cryptographic checker: whether
that key is authorized depends on ledger state, which is absent here.

## Reproducible fixture

The saved [hex bytes](fixtures/ml-dsa-44-accountset-v1.hex) and
[metadata](fixtures/ml-dsa-44-accountset-v1.json) represent one transaction
generated by the real native signer and independently verified by OpenSSL.
The fixture uses public test credentials; never use its keys for funds.
It has Account `r355VRk4DahGVPRN5Td4SqmhjB2hA1kt4s`, Sequence 1, and Fee 10.
Its transaction ID is
`AD4DA4CA47257A6A6E3D66060433374B7F14D04CEA8872291727A5DE89C640D7`.

The wire is 3782 bytes, containing a 1312-byte public key and 2420-byte
signature. The actual single-sign signing payload is 1363 bytes. The
candidate's `sizeof(PublicKey)` is 1320 bytes on this build; that is an object
layout observation, not an allocated-byte count or RSS measurement.

`replay_saved_wire_fixture` is a required test. It reads the saved hex into
an owned vector, verifies the wire SHA-256 and transaction ID, parses and
reserializes identical bytes, and checks both native and OpenSSL signature
verification. CMake also checks the hex-file hash against metadata. The wire
SHA-256 is
`d7fcc49c78df08883a7f412935e91ad9a5e7dbc6de02282536c1ee576f6a795c`.

Fresh fixture generation remains another test and uses real randomized
signing. It may produce a different valid signature and transaction ID on
each run. Reproducibility here means replaying the saved fixture; it does not
mean replacing the native RNG or assuming a seed determines signature bytes.

## Build

Use the already fetched [pinned checkouts](../README.md) and the existing
Ballast Conan toolchain. Enter Nix once, then run from the repository root:

```sh
nix develop .#gcc
cmake -S src/benchmarks/libxrpl/ballast/pq/native -B build/ballast-pq/native \
  -DCMAKE_TOOLCHAIN_FILE="$PWD/build/ballast-protocol/conan_toolchain.cmake" \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_UNITY_BUILD=ON -DCMAKE_UNITY_BUILD_BATCH_SIZE=15
cmake --build build/ballast-pq/native --parallel 2
ctest --test-dir build/ballast-pq/native --output-on-failure
```

Both algorithms in the native executable use the same candidate build and
object layout. In particular, the candidate has a 1312-byte inline PublicKey
buffer even for a secp256k1 key; comparing its future memory measurements to
the original root build requires disclosing that difference.

## Actual multisigning matrix

The separate `xrpl.ballast_pq_multisign` executable runs both algorithms in
the same pinned candidate build at 1, 8, and 32 signers. These are complete
AccountSet transactions with actual `Signers` arrays, not concatenated
independent records. The six saved hex/JSON pairs are in
[fixtures/multisign](fixtures/multisign).

| Signers | secp256k1 wire bytes | ML-DSA-44 wire bytes | Per-signer signing bytes, both |
| ---: | ---: | ---: | ---: |
| 1 | 181 | 3811 | 70 |
| 8 | 1108 | 30152 | 70 |
| 32 | 4283 | 120464 | 70 |

The common Account, Sequence, Flags, and Fee are identical across all six
cases. The account uses the earlier secp owner seed; only the signer algorithm
and signer array vary. The 50 common signing bytes, including the four-byte
multisigning prefix, are byte-identical across all cases. `sfSigners` is not
part of that payload. Each signer appends its raw 20-byte AccountID, producing
70 bytes to sign. The top-level SigningPubKey is empty for multisigning,
unlike the single-sign checkpoint's 1363-byte payload containing its public key.

Trace the eight-signer ML fixture through
[PqMultisign.cpp](../../../../../tests/libxrpl/ballast/PqMultisign.cpp):

1. `makeNativeMultisign()` creates the common fields, then obtains the 50 bytes
   from the native `startMultiSigningData()` serializer.
2. For each of eight deterministic signer keys it copies that serializer,
   calls `finishMultiSigningData(account, payload)`, and signs the resulting
   70 bytes using the native randomized ML signer.
3. Each STObject holds its Account, 1312-byte public key, and 2420-byte signature.
   The eight entries are sorted by binary AccountID. The first sorted signer
   in the saved fixture is `r3Ju896RA1QBNVdqMy66eakf8zwqJumjzc`.
4. The complete wire transaction occupies 30152 bytes. `SerialIter` parses it
   into STTx, whose `checkSign()` reconstructs the per-signer payload and checks
   every signature. OpenSSL independently verifies every ML signature.

Assembly finishes inside STTx's constructor callback, so its transaction ID
is calculated after signatures are attached. Each signer uses
`<signer_namespace>/signer/<decimal index>`; the same keys recur across counts.
All credentials are public test inputs. The owner is distinct from signers;
no ledger signer list, signer weights, or quorum is configured or checked.
Fee 10 remains a constant for controlling the common fields, not a fee
recommendation or evidence of network acceptance.

The matrix tests reject Sequence edits, a damaged **last** signature, relabeled
signer AccountIDs even after re-sorting, duplicate signers, and unsorted arrays.
Quantum-disabled rules reject ML-DSA and preserve secp256k1. Required replay
tests verify every saved fixture's wire hash, transaction ID, metadata sizes,
round trip, native signature result, and all ML signatures through OpenSSL.
CMake checks hex-file hashes against metadata at configuration time.

secp256k1 signatures are deterministic here: all three complete wire fixtures
match the original root-checkout controls byte for byte. ML-DSA signing uses
the real native RNG, so reproducibility uses the saved fixtures rather than
expecting fresh signing to reproduce signature bytes. The first eight signers
are reused at 32, but there is no public-key interning or other optimization.

## Actual validation

The earlier single-sign checkpoint on 2026-10-25 used GCC 15.3.0 / Release /
C++23 and OpenSSL 3.6.3 to build the
99 selected C++ sources plus the pinned reference C archive. CTest passed
**15/15 cases with no skips** in 0.35 seconds: eight native transaction checks
and the seven existing primitive interoperability checks. The native suite
also passed directly. The saved fixture passed replay in two additional
fresh processes with the same transaction ID.

Independent Python hashing confirmed both fixture fingerprints and the
transaction ID (`SHA512Half("TXN\0" || wire)`). All recorded candidate,
reference, and harness source hashes matched disk. Nix clang-format 23.1.0
and `git diff --check` passed; full pre-commit and full server tests were not run.
Both isolated source checkouts remained clean.

The subsequent matrix milestone, using the same compiler/dependencies,
passed **53/53 CTest cases with no skips** in 1.64 seconds. The 38 multisigning
checks also passed directly. All six saved fixtures passed replay in two
additional fresh processes. Independent Python checks verified every fixture
hash and TXN-prefixed transaction ID, the identical 50-byte shared payload,
all three secp control wires, and every final source-manifest hash. The previous
single-signed PQ fixture was preserved. Formatting and `git diff --check`
passed; no full server build, pre-commit suite, or ledger application was run.

Local artifacts live in `build/ballast-pq/native/`: `configure.log`,
`build-final.log`, `ctest-final.log`, `native.log`, `replay-1.log`,
`replay-2.log`, `fixture.bin`, `generated-fixture.log`, `source-sha256.txt`,
`native-sources.txt`, and `native-build-config.txt`. The fresh generation in
`native.log` can have a different ID from the saved fixture, as expected.
`generated-fixture.log` records the original saved fixture's generation.

The current matrix artifacts are `multisign-generation.log`,
`multisign-build-final.log`, `multisign-ctest.log`, `multisign-native.log`,
`multisign-replay-1.log`, `multisign-replay-2.log`, `multisign-fixtures.json`,
and `multisign-validation.json` in that same build directory. The source
manifest now records the expanded harness and all six saved fixture pairs.
The earlier single-sign validation report/logs are historical snapshots.

To replay only the saved matrix, inside Nix:

```sh
build/ballast-pq/native/xrpl.ballast_pq_multisign \
  --gtest_filter='Cases/BallastNativeMultisign.replays_saved_fixture_with_matching_identity_and_signatures/*'
```

The transaction fixture tests measure neither full-transaction heap allocations
nor RSS. The subsequent [accounting calibration](../../accounting/README.md)
adds controlled allocation tests, real single-field parser probes, and
separate `_counted` transaction regression copies. Build all targets above
before running the expanded CTest suite. The original test binaries remain
without the hook. The subsequent [measurement milestone](../../measurement/README.md)
now emits scoped transaction CSVs using the saved matrix; its own CSV/JSON
metadata describes measured boundaries and coverage.

These tests perform no
ledger authorization, fee validation, transaction application, or network
submission. These checks establish selected functional behavior on the pinned
experimental implementation; it is not a production readiness claim.
